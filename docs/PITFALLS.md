# YuMi-cute 踩坑记录

> 这个文件记录我在做这个项目的过程中踩过的每一个坑。
>
> 它们比"顺利跑通"更有价值——因为每一个坑都对应一个真实的知识点，也对应面试里的一个问题。
>
> 每次踩新坑就往这里加一条。面试前翻一遍，就是最好的复习材料。

---

## 一、环境类

### 1. JDK 版本过低

- **现象**：Spring Boot 3 项目起不来
- **原因**：Spring Boot 3 要求 Java 17+，本机装的是 Java 8
- **解决**：装 JDK 21，改 `JAVA_HOME` 和 `PATH`
- **记住**：框架对 JDK 版本有硬性要求，不是"最好升级"，是"不升级寸步难行"

### 2. Maven 下载依赖极慢

- **解决**：在 `~/.m2/settings.xml` 里配阿里云镜像
- **记住**：国内开发，所有包管理器（Maven / npm / pip）都要配国内源

### 3. `wsl --install` 报 403

- **现象**：命令返回"已禁止(403)"
- **原因**：`wsl --install` 在联网下载组件时被挡
- **解决**：手动启用 Windows 功能（适用于 Linux 的 Windows 子系统 + 虚拟机平台）→ 重启 → 再装
- **记住**：Windows **家庭版没有 Hyper-V**，WSL2 是唯一的路

### 4. Docker 拉镜像报 `denied`

- **现象**：`docker pull minio/minio` 返回 `error from registry: denied`
- **原因**：镜像加速源不服务该镜像，或官方仓库调整了分发策略
- **记住**：Docker 镜像问题在国内是常态，**不是你的操作有问题**

### 5. MinIO 官网下载只有 11.7 KB/s

- **现象**：能下载，但 120MB 的文件要三个多小时
- **最终决策**：**放弃 Docker / MinIO**，改用"面向接口 + 本地磁盘实现"
- **收尾**：写了一个 `FileStorage` 接口 + `LocalFileStorage` 实现，将来网络好了只需新增一个 `MinioFileStorage`
- **记住**：**环境的坑不该拖住进度。好的抽象让"换实现"的代价极小。**

（旧下载地址 `dl.min.io/server/...` 已失效，新地址是 `dl.min.io/aistor/minio/...`）

## 二、数据库类

### 6. `Column 'biz_id' cannot be null`

- **现象**：注册时插入 `points_record` 失败，用户注册不上
- **原因**：`biz_id BIGINT NOT NULL DEFAULT 0`，但 INSERT 语句**显式写了这一列**并传了 `null`
- **★ 记住**：**`DEFAULT` 只在"语句里不写这一列"时才生效。一旦显式写了并传 null，默认值不兜底，直接被 `NOT NULL` 拦下。**

### 7. `Column 'error_msg' cannot be null`（同一个坑的复刻！）

- **现象**：异步生成的第一张图状态写不进去，订单永远卡在"生成中"
- **原因**：`updateResult(id, status, imageUrl, errorMsg)` **一个方法更新所有字段**，成功时 `errorMsg` 只能传 `null`
- **解决**：拆成 `markSuccess` / `markFailed`，**每个方法只写自己该写的列，不碰不相干的列**
- **★ 记住**：**"一个方法更新所有字段"会逼你给用不上的字段填空值——这是坑的温床。**

### 8. 自增 id 出现空洞

- **现象**：注册失败后，下一个成功的用户 id 跳过了失败的号
- **原因**：事务回滚**不会**回滚自增计数器
- **记住**：正常现象，不用担心。回滚的是数据，不是序号。

### 9. 时间差 8 小时

- **解决**：JDBC URL 加 `serverTimezone=Asia/Shanghai`

### 10. 中文 / emoji 乱码

- **记住**：建表一律用 `utf8mb4`。MySQL 的 `utf8` 只能存 3 字节，存不了 emoji。

### 11. `pet_id` 不允许为空，但第一版不需要宠物档案

- **原因**：设计阶段超前设计了，实际 MVP 不做宠物管理
- **解决**：`ALTER TABLE photo_order MODIFY COLUMN pet_id BIGINT NULL`
- **★ 记住**：表结构随产品范围演进很正常，不是设计失败。但**改完一定要同步更新 `sql/schema.sql`**。

## 三、后端逻辑类

### 12. "先查再插"，并发下用户名重复

- **原因**：check-then-act 竞态——两个请求同时通过"用户名不存在"的检查
- **解决**：数据库唯一索引兜底 + 捕获 `DuplicateKeyException`
- **★ 记住**：**应用层查重管"体验"，数据库唯一索引管"正确性"。两者缺一不可。**

### 13. 扣算力超扣

- **原因**：同样是 check-then-act——"查余额 → 判断够不够 → 扣减"分了三步
- **解决**：合并成一条 SQL
  ```sql
  UPDATE `user` SET points = points - #{cost} WHERE id = #{userId} AND points >= #{cost}
  ```
  看影响行数：0 就是余额不足
- **★ 记住**：**代码里分两步的地方，并发时就会出问题。能合成一步的，就合成一步。**

### 14. 事务范围过大

- **现象**：`@Transactional` 加在了 `UserService` 类上，连纯查询的 `login` 也开事务
- **解决**：挪到真正需要事务的方法上（比如 `register`，它要同时写两张表）
- **★ 记住**：**事务越小越好。** 事务开着会占住数据库连接、持有锁。

### 15. ★ 异步任务整个崩溃（最惨的一次）

- **现象**：订单永远卡在"生成中"，任务永远卡在"排队中"
- **根因链**：
  1. `NOT NULL` 的列传了 `null` → 第一次 UPDATE 失败
  2. 进入 `catch` 块补救 → **补救代码也抛异常**（另一个字段也是 `NOT NULL`）
  3. 这个异常**没有被任何代码接住**，直接飞出 `@Async` 方法 → 循环终止
- **解决**：三层防护
  - 内层 `try`：单张失败只标记这一张，继续做下一张
  - 内层 `catch` 里再包一层 `try`：**连"写失败状态"都可能失败，不能让它带崩循环**
  - **最外层 `finally`：无论如何，订单最终状态一定要被写一次**
- **★ 记住**：
  - **"处理失败"的代码自己也会失败。**
  - **状态机必须有终点。** 永远停在"生成中"比明确显示"生成失败"糟糕一百倍。

### 16. 异步任务在事务提交前被触发

- **原因**：在 `@Transactional` 的 `createOrder` 内部就调用了 `@Async` 方法，异步线程读不到还没提交的订单
- **解决**：在**事务外面**（Controller 里）触发异步
- **★ 记住**：**异步任务涉及的数据，必须在触发之前就已经落库。**

### 17. `@Async` / `@Transactional` 同类自调用失效

- **原因**：两者都靠 Spring 的代理实现。同一个类里 `this.方法()` 调用绕过代理，注解不生效
- **解决**：把需要注解的方法放到**另一个 Bean** 里
- **记住**：写补偿任务时又碰到一次——调度器类和业务类必须分开

## 四、前后端联调类

### 18. 跨域被浏览器拦下

- **现象**：`has been blocked by CORS policy`
- **原因**：前端 5173、后端 8080，端口不同 → 触发浏览器同源策略
- **解决**：开发环境用 Vite 代理（`/api` → `localhost:8080`），生产环境用 Nginx 反向代理
- **★ 记住**：
  - **是浏览器拦的，不是服务器。** 服务器其实正常返回了，是浏览器把响应扣下了。
  - **Postman 测同一个接口不会跨域**，因为它不是浏览器。

### 19. `ECONNREFUSED`（Vite 代理报错）

- **现象**：前端终端里 `http proxy error ... ECONNREFUSED`
- **原因**：后端根本没启动，8080 上没有程序在监听
- **★ 记住**：几种错误一眼区分

  | 报错 | 含义 |
  |---|---|
  | `ECONNREFUSED` | 端口上没有程序在监听 → **后端没启动** |
  | `ETIMEDOUT` | 连不上 → 地址不对 / 网络不通 |
  | `404` | 连上了，路径不存在 |
  | `500` | 连上了，后端处理时崩了 |
  | CORS 报错 | 连上了也返回了，但被浏览器扣下 |

### 20. 上传大图失败

- **现象**：`Maximum upload size exceeded`
- **原因**：**Spring Boot 默认单文件上限只有 1MB**
- **解决**：
  ```yaml
  spring:
    servlet:
      multipart:
        max-file-size: 10MB
        max-request-size: 20MB
  ```
- **★ 记住**：**框架的默认值往往不适用于真实场景。**

### 21. 手动设置 multipart 的 `Content-Type` 导致上传失败

- **原因**：multipart 的 Content-Type 后面必须带浏览器自动生成的 `boundary`，手动写死会把它覆盖掉
- **解决**：什么都不写，交给 axios 自动处理
- **★ 记住**：**别覆盖浏览器自动生成的东西。**

### 22. 同一个文件选第二次不触发 `change`

- **原因**：`<input type="file">` 的值没变，浏览器认为"没变化"
- **解决**：上传完成后 `event.target.value = ''`
- **记住**：很隐蔽，但一定会遇到

### 23. 定时器忘记清理

- **原因**：组件销毁了，但 `setInterval` 还活着，继续发请求
- **解决**：`onUnmounted(stopPolling)`
- **★ 记住**：**只要用了"组件之外的东西"（定时器、事件监听、WebSocket），就必须在 `onUnmounted` 里清掉。**

### 24. `v-for` 的 `key` 用 index 导致状态串位

- **解决**：用数据自己的唯一 id 当 key

## 五、安全类

### 25. 接口把密码字段返回给了前端

- **解决**：`@JsonIgnore`；更规范的是用 VO 只暴露该给的字段
- **★ 记住**：**Entity 永远不直接和前端打交道。DTO 管进，VO 管出。**

### 26. 用户名枚举漏洞

- **现象**：如果"用户不存在"和"密码错误"分开提示，攻击者能刷出所有已注册用户名
- **解决**：统一返回"用户名或密码错误"
- **★ 记住**：**认证失败时，绝不告诉对方是哪一步错了。**

### 27. SQL 注入风险

- **★ 记住**：**能用 `#{}` 就永远不要用 `${}`。** `#{}` 是预编译参数，`${}` 是字符串拼接。

### 28. 水平越权（IDOR）

- **现象**：把 `/orders/5` 改成 `/orders/6` 就能看到别人的订单
- **解决**：SQL 里带上归属条件
  ```sql
  WHERE o.id = #{id} AND o.user_id = #{userId}
  ```
- **★ 记住**：**归属校验必须做在查询里，不能只在 Java 里补一句判断。** 查不到就统一说"不存在"，不给攻击者任何线索。

### 29. 越权的"我是谁"永远从 token 取，不从请求参数取

- **记住**：如果让前端传 `userId`，用户就能改别人的数据。**永远不信任客户端声称的身份。**

## 六、设计理念类（不算是坑，但比坑更重要）

### 30. 面向接口编程 —— 用了两次，救了两次

| 场景 | 接口 | 实现 |
|---|---|---|
| 文件存储 | `FileStorage` | `LocalFileStorage` / （将来）`MinioFileStorage` |
| 图片生成 | `PhotoGenerator` | `MockPhotoGenerator` / （将来）`AiPhotoGenerator` |

- **记住**：**把"会变的东西"抽到接口后面，业务代码只依赖接口。** 换实现时，上层一行都不用改。
- 这是 MinIO 装不上时，整个项目还能继续往前走的原因。

### 31. 业务规则只能有一个来源

- **现象**：试看价的规则（整套价 ÷ 4）在前端和后端各写了一遍
- **风险**：改了一处忘了另一处 → 界面显示 5 算力、实际扣 7 算力
- **待还的技术债**：由后端在 `/style/list` 里直接返回 `trialPointsCost`
- **★ 记住**：**同一套业务规则在两处各写一份，是隐患。**
